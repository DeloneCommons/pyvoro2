# v0.9 post-functional audit backlog

**Status:** Living, non-normative intake.

This document collects cross-cutting questions and findings discovered during
Phase B, Phase C, WP10–WP13, and ordinary implementation or review. It is an
inbox for the [already-planned post-functional reread and audit](../plans/v0.9.md#post-functional-pre-release-maturation),
not a second roadmap or a new feature phase.

Entries are observations/questions, **not accepted requirements**. Adding an
entry does not amend an ADR, public API contract, work package, qualification
policy, or release requirement. Implementation requires explicit later
disposition during the post-functional audit/remediation stage and acceptance
as pre-release remediation, with any necessary contract updates made through
the normal [development workflow](../development-workflow.md).

## Intake and disposition

- Add a stable ID, concrete question, affected surfaces, and source/review
  evidence. Keep observations distinct from possible solutions.
- Record current behavior against an identifiable source or artifact; refresh
  it during audit rather than assuming it remains unchanged.
- Consolidate duplicate or overlapping observations during audit while
  preserving their IDs and evidence.
- Record the decision, rationale, and references when triaging an entry.
  Outcomes may be **rejected**, **documentation-only**, **accepted for
  pre-release remediation**, or **deferred** with a reason and target stage.
- Only explicitly accepted pre-release findings become implementation work.
  A dedicated audit/remediation tracker may be opened at that future stage,
  once the completed code and backlog establish its scope.

The release sequence remains functional completion, whole-code maintainer
comprehension reread, separate architectural/technical audit, focused
remediation of accepted findings if any, documentation overhaul, then final
frozen-source qualification/release. The v0.9.x **soak** is the later period
of real downstream use after v0.9.0, as defined by
[ADR 0017](../decisions/0017-v0.9-functional-stabilization-before-1.0.md).

## Open questions

### PA-001 — Should qualification gate guarantees, result availability, or both?

- **ID:** PA-001
- **Area:** Native qualification and public result availability.
- **Category:** `proof-policy`, `API/UX`, `architecture`, `downstream-need`.
- **Question / observation:** Phase B qualification establishes whether an
  artifact is entitled to strong pyvoro2 certification guarantees. Some current
  routes also use missing qualification as a hard availability gate. Should
  pyvoro2 distinguish certified results, explicitly unverified/best-effort
  numerical results, and operations that must hard-refuse because their
  downstream semantics logically depend on certified provenance?
- **Why revisit:** Inability to prove the strongest certificate is not the
  same claim as practical numerical uselessness. The current availability
  policy may be too restrictive for some users; a whole-system review should
  assess usefulness, truthful guarantees, and consumer requirements together.
- **Affected surfaces:** Ordinary `pyvoro2.planar.compute`; periodic face/edge
  image metadata; ghost boundary provenance; periodic `locate` owner-image
  metadata; realization-aware inverse workflows. These are representative
  surfaces to inspect, not a claim that they require identical policy.
- **Current behavior:** At reviewed `dev`
  `032c0d5befeb88b4a903274d082029c30fcc882f`, ordinary planar `compute()`
  always enters the source-witness/certification route and has no unqualified
  geometry-only fallback. Profile failures become structured hard refusals.
  Phase B is hardening qualification admission for the accepted native
  contracts; its current contract remains authoritative.
- **Potential direction(s), if any:** An explicit qualification/trust mode,
  result capability/trust metadata, or another cleaner design could be
  considered. No option is selected; retaining the current refusal policy is
  also an available disposition if justified by the audit.
- **Evidence / references:**
  [Phase B qualification hardening](../plans/v0.9.md#phase-b-qualification-hardening-generalize-native-certificate-profiles),
  [issue #88](https://github.com/DeloneCommons/pyvoro2/issues/88),
  [reviewed planar compute routing](https://github.com/DeloneCommons/pyvoro2/blob/032c0d5befeb88b4a903274d082029c30fcc882f/src/pyvoro2/planar/api.py),
  [reviewed planar profile admission](https://github.com/DeloneCommons/pyvoro2/blob/032c0d5befeb88b4a903274d082029c30fcc882f/src/pyvoro2/_internal/planar/wp6_profile.py),
  and [ADR 0022](../decisions/0022-wp6-source-certified-planar-edge-provenance.md).
- **Decision status:** Open — no design selected or implementation authorized.
- **Decision deadline / stage:** Post-functional audit/remediation, before
  v0.9 public API/documentation freeze and final release qualification.
- **Notes:** This entry does not weaken or alter Phase B admission or any
  accepted certificate/provenance contract. Recheck the completed source at
  audit time and decide per surface which guarantees its consumers require.
