# v0.9 whole-code audit backlog

**Status:** Living, non-normative intake.

This document collects cross-cutting questions and findings discovered during
Phase B, Phase C, WP10–WP13, and ordinary implementation or review. It is an
inbox for the [pre-Phase-D reread and audit](../plans/v0.9.md#pre-phase-d-gate-whole-code-comprehension-and-audit)
and subsequent post-WP13 delta review,
not a second roadmap or a new feature phase.

Entries are observations/questions, **not accepted requirements**. Adding an
entry does not amend an ADR, public API contract, work package, qualification
policy, or release requirement. Implementation requires explicit later
disposition during the pre-Phase-D audit or post-WP13 delta review and acceptance
as pre-release remediation, with any necessary contract updates made through
the normal [development workflow](../development-workflow.md).

## Intake and disposition

- Add a stable ID, concrete question, affected surfaces, and source/review
  evidence. Keep observations distinct from possible solutions.
- Record current behavior against an identifiable source or artifact; refresh
  it during audit rather than assuming it remains unchanged.
- Consolidate duplicate or overlapping observations during audit while
  preserving their IDs and evidence.
- Record the decision, rationale, and references when triaging an entry.
  Outcomes may be **rejected**, **documentation-only**, **accepted for
  pre-release remediation**, or **deferred** with a reason and target stage.
- Only explicitly accepted pre-release findings become implementation work.
  When actionable, one recovery umbrella owns reread/reconciliation, audit,
  disposition and accepted remediation closure or explicit none required.
  Create remediation children JIT only for accepted findings, and a separate
  remediation umbrella only when multiple children need coordination.

## Open questions

### PA-001 — Should qualification gate guarantees, result availability, or both?

- **ID:** PA-001
- **Area:** Native qualification and public result availability.
- **Category:** `proof-policy`, `API/UX`, `architecture`, `downstream-need`.
- **Question / observation:** Phase B qualification establishes whether an
  artifact is entitled to strong pyvoro2 certification guarantees. Some current
  routes also use missing qualification as a hard availability gate. Should
  pyvoro2 distinguish certified results, explicitly unverified/best-effort
  numerical results, and operations that must hard-refuse because their
  downstream semantics logically depend on certified provenance?
- **Why revisit:** Inability to prove the strongest certificate is not the
  same claim as practical numerical uselessness. The current availability
  policy may be too restrictive for some users; a whole-system review should
  assess usefulness, truthful guarantees, and consumer requirements together.
- **Affected surfaces:** Ordinary `pyvoro2.planar.compute`; periodic face/edge
  image metadata; ghost boundary provenance; periodic `locate` owner-image
  metadata; realization-aware inverse workflows. These are representative
  surfaces to inspect, not a claim that they require identical policy.
- **Current behavior:** At integrated `dev`
  `f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1`, ordinary planar
  `compute()` still consumes the source-witness/certification route and has
  no unqualified geometry-only fallback. Missing or incompatible qualification
  produces a structured hard refusal for the affected certificate-bearing
  route. Phase B / issue #88 is independently accepted and merged; this entry
  questions later product policy, not the accepted qualification mechanism.
- **Potential direction(s), if any:** An explicit qualification/trust mode,
  result capability/trust metadata, or another cleaner design could be
  considered. No option is selected; retaining the current refusal policy is
  also an available disposition if justified by the audit.
- **Evidence / references:**
  [Phase B qualification hardening](../plans/v0.9.md#phase-b-qualification-hardening-generalize-native-certificate-profiles),
  [issue #88](https://github.com/DeloneCommons/pyvoro2/issues/88),
  [reviewed planar compute routing](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/src/pyvoro2/planar/api.py),
  [reviewed planar profile admission](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/src/pyvoro2/_internal/planar/wp6_profile.py),
  [ADR 0022](../decisions/0022-wp6-source-certified-planar-edge-provenance.md),
  and [ADR 0024](../decisions/0024-external-native-artifact-qualification.md).
- **Decision status:** Open — no design selected or implementation authorized.
- **Decision deadline / stage:** Post-functional audit/remediation, before
  v0.9 public API/documentation freeze and final release qualification.
- **Notes:** This entry does not weaken or alter Phase B admission or any
  accepted certificate/provenance contract. Recheck the completed source at
  audit time and decide per surface which guarantees its consumers require.


### PA-002 — How should qualification interact with import/loader instrumentation?

- **ID:** PA-002
- **Area:** Native artifact identity, import registration, and development tooling.
- **Category:** `proof-policy`, `API/UX`, `testing-gap`, `documentation`,
  `maintenance`.
- **Question / observation:** The Phase-B trust boundary deliberately binds the
  loaded native payload and loader-visible identity. Instrumentation that wraps
  or substitutes import/loader behavior can therefore cause qualification
  refusal even when an ordinary direct import succeeds. Is that refusal the
  desired user-facing boundary for all supported testing/profiling tools, or
  should some transparent instrumentation receive a reviewed compatibility
  path?
- **Why revisit:** Correct fail-closed behavior can still be surprising in
  developer environments. The post-functional audit should separate necessary
  artifact-identity protection from avoidable friction and decide whether code,
  diagnostics, or documentation should change.
- **Affected surfaces:** Native import registration and qualification loading,
  pytest/plugin instrumentation, tracing/profiling/coverage environments, and
  qualification diagnostics.
- **Current behavior:** At integrated `dev`
  `f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1`, qualification verifies the
  actual imported native payload and loader/mapping evidence and refuses
  mismatched or wrapped identities. The independent final #88 review observed
  an automatically instrumented pytest import being refused while ordinary
  direct import succeeded; controlled reruns without that instrumentation
  passed.
- **Potential direction(s), if any:** Retain the current refusal and document
  supported environments; improve diagnostics; or define a narrowly reviewed
  proof-preserving compatibility route for specific instrumentation. No option
  is selected.
- **Evidence / references:** [ADR 0024](../decisions/0024-external-native-artifact-qualification.md),
  [native qualification implementation](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/src/pyvoro2/_internal/native_qualification.py),
  [import-loader tests](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/tests/tooling/test_native_import_loader.py),
  and [PR #90](https://github.com/DeloneCommons/pyvoro2/pull/90).
- **Decision status:** Open — no implementation authorized.
- **Decision deadline / stage:** Post-functional audit/remediation, before the
  final documentation and release-qualification stages.
- **Notes:** Do not weaken artifact identity merely to accommodate test tooling;
  first establish whether a proposed compatibility path preserves the accepted
  qualification trust boundary.

### PA-003 — Must every integration push run the full native qualification matrix?

- **ID:** PA-003
- **Area:** CI routing and qualification cost.
- **Category:** `performance`, `maintenance`, `testing-gap`, `proof-policy`.
- **Question / observation:** Pull requests use changed-path classification, but
  non-PR integration pushes currently route through `--full`, so every push
  to `dev` or `main` runs the complete qualification matrix. Is this
  conservative policy still the right cost/reliability tradeoff once the v0.9
  architecture has stabilized?
- **Why revisit:** The full matrix is intentionally fail-closed and supplied
  valuable integration evidence during Phase B, but it is expensive. A later
  whole-system audit can decide whether exact integration qualification must
  remain universal or whether an equally defensible closure-aware strategy can
  reduce routine CI cost.
- **Affected surfaces:** `.github/workflows/ci.yml`,
  `tools/ci_classify_changes.py`, protected-branch required checks, scheduled
  qualification, and release qualification.
- **Current behavior:** At integrated `dev`
  `f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1`, pull requests classify their
  complete diff, while non-PR pushes invoke the classifier with `--full`.
  The post-merge issue-#88 integration run therefore reran FULL qualification
  and passed.
- **Potential direction(s), if any:** Keep FULL integration pushes; use a
  rigorously reviewed integration-diff classifier plus targeted smoke checks;
  move some complete matrices to scheduled/release gates; or another design
  that preserves fail-closed required evidence. No option is selected.
- **Evidence / references:** [CI workflow](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/.github/workflows/ci.yml),
  [change classifier](https://github.com/DeloneCommons/pyvoro2/blob/f2f9b3161c3b1fbd9ccfba3b563fbe4057cc13f1/tools/ci_classify_changes.py),
  and [post-merge CI run 36717984495](https://github.com/DeloneCommons/pyvoro2/actions/runs/36717984495).
- **Decision status:** Open — no CI policy change authorized.
- **Decision deadline / stage:** Post-functional audit/remediation, before final
  release qualification and long-term v0.9.x maintenance policy is frozen.
- **Notes:** CI cost alone is not evidence that qualification coverage is
  redundant. Any reduction must preserve the proof-relevant invalidation model.
