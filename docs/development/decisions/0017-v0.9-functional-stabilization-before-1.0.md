# 0017 — Functional stabilization precedes 1.0 and later inverse families

- **Status:** Accepted
- **Date:** 2026-08-16
- **Amended:** 2026-09-16
- **Supersedes:** only the post-v0.8 feature sequence stated in
  [ADR 0006 — v0.8 is a technical-maintenance release](0006-v0.8-cleanup-release.md)
- **Related roadmap:** [Project roadmap](../../project/roadmap.md)
- **Related plan:** [v0.9.0 development plan](../plans/v0.9.md)

## Context

ADR 0006 correctly separated the feature-free v0.8 cleanup from future inverse
features, but its provisional sequence placed prescribed cell measures in v0.9
and mixed fitting in v0.10.

A later code-first capability review and downstream planning exposed a more
important pre-1.0 need. pyvoro2 is intended to serve application packages such
as chemvoro, where ordinary workloads include weighted molecular geometries,
periodic crystals, and repeated independent simulation frames. The current
forward and periodic APIs still contain wrapper-level restrictions and
representation-sensitive behaviors that are reasonable to correct before a
stable release. v0.9 is also the last inexpensive point for deliberate public
API refinement based on real downstream use.

The existing separator inverse layer is already the principal inverse
functionality needed by that downstream use. Its fixed-observation inner solve
has an exact/convex mathematical contract, while realization-aware active-set
refinement is an empirical outer algorithm. Calling the entire
realization-aware workflow experimental indefinitely would conflate algorithmic
convergence guarantees with API stability: an iterative method can have a
stable supported input/result/status contract while still returning cycles,
iteration limits, infeasibility, or numerical failure for some inputs.

Prescribed cell measures and mixed observation families are valuable, but they
are not required to make the existing package a credible 1.0 dependency.

## Decision

The post-v0.8 sequence is changed as follows:

1. **Development through v0.9.0 is the main functional/API stabilization and
   pre-release maturation phase; released v0.9.x is the
   downstream-readiness/soak phase.** v0.9.0 may
   make deliberate documented pre-1.0 API changes and remove artificial
   forward/periodic restrictions that materially affect intended downstream
   workflows. It does not add a new inverse observation family merely to fill
   the version, and it is not required to complete the later real-world soak
   before it can be released.
2. **The normal realization-aware separator inverse workflow is a v0.9
   stabilization target.** By the end of v0.9, ordinary downstream callers
   should not need an API labelled experimental to perform the supported
   "points + separator observations -> fitted weighted tessellation" workflow.
   Stable public semantics do not imply a universal convergence theorem for the
   empirical outer refinement. Advanced research/path internals may remain
   provisional when the normal high-level contract does not depend on them.
3. **Post-functional pre-release review is explicit and precedes the large
   documentation pass.** After WP1-WP13, the maintainer first rereads the
   complete resulting codebase to restore an informed whole-system model and
   reconcile it with the architecture documentation. A separate evidence-driven
   architectural and technical audit then examines reasonably discoverable
   internal weaknesses. Findings explicitly accepted for pre-release
   remediation are resolved before documentation if any; otherwise the project
   moves directly to the documentation phase. These stages are neither part of
   the WP1-WP13 functional/API tracker nor part of final frozen-source release
   qualification.
4. **Documentation is overhauled before v0.9.0 is frozen and released.** Factual
   API/capability alignment continues alongside functional implementation. Once
   post-functional review and any remediation explicitly accepted for
   pre-release work are complete, the documentation workstream migrates the
   current Markdown-first stack to Zensical, preserves the notebook source/export
   workflow, and verifies the required API-reference, MathJax,
   Markdown-extension, snippet, and related capabilities before switching. It
   performs a low-redesign compatibility migration first, then improves content
   and information architecture, visual/navigation design, and the project
   landing page. Documentation CI and deployment change only after the
   replacement stack is verified.
5. **Final frozen-source qualification follows all release-blocking
   implementation, review, remediation, and documentation work.** It validates
   a source candidate that is no longer changing and remains distinct from the
   earlier API review, whole-code comprehension pass, architectural audit, and
   downstream soak.
6. **1.0 follows a successful v0.9.x soak and stabilizes the existing forward,
   periodic, and separator-inverse core.** The soak must reveal no critical
   correctness/API hole requiring another incompatible redesign, and downstream
   callers should not require private APIs or manual workarounds. Prescribed-
   measure and mixed inverse solvers are not gates for 1.0.
7. **v1.1 targets prescribed cell measures.** The solver family remains shared
   with the existing inverse architecture rather than being introduced as an
   unrelated utility.
8. **v1.2 targets mixed separator-plus-measure fitting.** Built-in per-row,
   per-site, and block-scaling needs should be understood before freezing any
   generic public observation-block protocol.
9. **pyvoro2 remains one repository and one distribution through 1.0.** A
   post-1.0 split is reconsidered only under a concrete trigger, especially a
   credible alternative Voronoi backend with an existing Python interface that
   makes backend-neutral inverse logic practically valuable.
10. The roadmap records potentially valuable wrapper, periodic, inverse, and
   post-1.0 workstreams so they are not lost. Concrete issue grouping and exact
   release acceptance criteria are intentionally deferred to development plans
   and GitHub issue design.

This decision does **not** change v0.8 scope or reopen completed v0.8 work.

## Consequences

- The accepted v0.8 technical-maintenance decision remains intact; only its old
  post-v0.8 feature ordering is superseded.
- v0.9.0 becomes the main opportunity to qualify and, where justified, refine
  the public API before the stronger 1.0 compatibility commitment; released
  v0.9.x then supplies external downstream evidence.
- The released-v0.9.x soak is reserved primarily for evidence that requires
  real downstream use, integration pressure, workload diversity, or operational
  experience rather than for internal weaknesses reasonably discoverable by a
  deliberate pre-release whole-system review.
- Downstream chemistry-facing validation is evidence for API readiness without
  moving chemistry-specific models or structure parsing into pyvoro2.
- Molecule, crystal, and repeated-frame use does not by itself imply a
  persistent trajectory/container API; independent frame computation is enough
  for the pre-1.0 contract unless profiling establishes a separate need.
- The realization-aware separator algorithm can remain explicitly described as
  empirical and non-universally-convergent while its supported public workflow
  is promoted out of the experimental lifecycle category.
- Prescribed-measure and mixed research work no longer delay the stable 1.0
  release.
- Zensical is the accepted pre-release documentation direction, but the switch
  occurs only after required current capabilities are verified and a
  compatibility migration succeeds.
- The one-repository/one-distribution boundary is stable through 1.0 rather than
  being reopened issue-by-issue during v0.9.

## Decisions intentionally left open

The one-repository/one-distribution policy is settled above. One backend policy
remains intentionally open until v0.9 implementation supplies the evidence
needed to choose it responsibly:

- whether pyvoro2 should require functionally unmodified upstream Voro++ source,
  or permit a bounded, explicitly maintained downstream patchset that does not
  amount to an independently evolving pyvoro2 backend fork.

WP7 is the intended evidence-gathering point because current source establishes
the need for a narrow 3D ghost native-bridge correction but does not establish
that vendored Voro++ source must change. WP7 must first determine whether a
clean binding-only correction is sufficient. Such a correction does not itself
settle this policy.

If WP7 demonstrates that a vendored Voro++ source change is necessary, it must
reduce that need to the minimum concrete diff and stop before accepting the
patch while the maintainer settles the policy. The decision is not defined
solely by whether a downstream patch is temporary: a possible bounded-patchset
policy may allow narrow long-lived patches, including patches upstream does not
adopt, when they are explicit, isolated, regression-tested, and reviewed during
every vendor update. That possibility is not authorization to carry such a
patch before D9 is decided.

A proposal that materially changes Voro++ geometry algorithms, numerical
behavior, or core backend architecture exceeds this bounded policy question and
requires a separate maintainer-level architecture decision.

## Alternatives considered

### Keep prescribed measures in v0.9 and mixed fitting in v0.10

Rejected. Those features are scientifically useful but are not the limiting
factor for the immediate downstream package. Adding them before correcting
avoidable forward/periodic friction would spend the remaining pre-1.0 API
freedom on the wrong priority.

### Add v0.9 functional stabilization, then still require v0.10/v0.11 inverse features before 1.0

Rejected. A stable release can be based on the already substantial forward and
separator-inverse functionality once it is validated by real downstream use.
There is no architectural reason for a second observation family to be a 1.0
gate.

### Keep the realization-aware separator workflow experimental through 1.0

Rejected as a blanket policy. Lack of a universal outer-loop convergence theorem
is a scientific limitation to document, not by itself a reason to deny stable
API status to the package's main downstream inverse workflow. Stable status
must instead be earned through clear supported inputs, inspectable termination,
consistent final-state semantics, tests, and downstream use.
