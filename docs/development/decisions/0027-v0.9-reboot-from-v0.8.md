# 0027 — Restart v0.9 development from published v0.8.0

- **Status:** Accepted
- **Date:** 2026-10-08
- **Transition:** [Issue #120](https://github.com/DeloneCommons/pyvoro2/issues/120)
- **Supersedes:** the future release sequence and mandatory outcomes in
  [ADR 0017](0017-v0.9-functional-stabilization-before-1.0.md)

## Context

The previous v0.9 attempt accumulated useful implementation, tests, numerical
counterexamples, and design evidence, but is no longer the development base.
The maintainer approved restoring an understandable operational workflow from
published v0.8.0 before choosing future geometric architecture.

The historical source is available through the
[protected archive](https://github.com/DeloneCommons/pyvoro2/tree/archive/v0.9-attempt-2026-10-08).
It was not released as v0.9.0. At transition start, `main` and `v0.9-reboot`
point to the baseline, while old `dev` points to the historical attempt.
Branch cutover is a separate operation under issue #120.

## Decision

1. Develop from the published v0.8.0 source on protected `v0.9-reboot`, using
   focused feature PRs. Preserve implemented v0.8 numerical and public behavior
   unless a separate approved task changes it.
2. **PR1 owns operational bootstrap:** routine CI with a fail-closed required
   `CI gate`, standard editable development, concise agent policy, this decision
   and planning corrections, `0.9.0.dev0` metadata, source-version/tag matching,
   and main-only production documentation deployment. It does not redesign
   geometry, change APIs, or qualify a release.
3. **PR2 owns curated historical knowledge migration:** requirements, accepted
   and unfinished results, WP1–WP11, remediation, known defects, evidence, and
   independent oracles. Adoption into the reboot starts **unreviewed** unless
   explicitly approved. PR1 does not perform that inventory or import evidence.
4. Historical ADRs **0018–0026 are not automatically adopted**. Their numbers
   stay reserved; this decision deliberately uses 0027. Historical designs,
   tests, and source are evidence to assess, not binding reboot architecture.
5. Historical **Checkpoint C remains pending/unaccepted**. Pre-Phase-D recovery
   and WP12/WP13 remain unfinished. Archiving, merging remediation, or starting
   the reboot does not accept them.
6. Future geometry architecture and future release scope are **undecided**.
   ADR 0017's mandatory v0.9, 1.0, v1.1, and v1.2 outcomes no longer govern.
   Superseding it does **not** reactivate ADR 0006's earlier feature sequence.
   Completed v0.8 decisions and behavior remain the baseline.
7. Prescribed-cell-measure inversion and mixed separator-plus-measure inversion
   are **possible research candidates only**. Neither implementation, public
   API, architectural relationship, release target, nor pre-1.0 inclusion is
   approved. Either candidate requires separate mathematical analysis,
   representative use cases, a validation strategy, and maintainer approval
   before implementation. Earlier future-facing architectural prescriptions
   do not settle those choices for the reboot.
8. Numerical changes require focused regressions and independent analytic or
   mathematical oracles wherever practical. Preserve known safety evidence for
   later assessment; do not assume self-consistency or legacy test success
   proves scientific correctness. Unexplained numerical differences require
   investigation, not silent acceptance.

## Consequences

Routine CI runs Linux Python 3.10 and 3.14 plus lint/synchronization, unchanged
native-safety coverage, and distribution validation. An explicit manual
`extended` input expands testing to Linux, macOS, and Windows on Python
3.10–3.14. Every required dependency must succeed for `CI gate` to succeed.
Production Pages deployment is restricted to `main`.

The normal development environment uses scikit-build-core's existing editable
installation. Existing Python-source edits normally need no rebuild; native,
build, ABI, metadata/dependency, or package-discovery changes may need one.
Installed-package provenance checks remain separate from editable testing.

PR1 implementation ends at PR creation after bounded local validation. Actual
PR checks and implementation receive independent review in a separate session;
integration and post-merge validation require the downstream maintainer step.
This record grants no merge, branch-cutover, checkpoint, API-freeze, or release
acceptance authority.

## Alternatives considered

- Continue the historical v0.9 implementation: not selected as the reboot base;
  preserve it permanently as evidence instead.
- Import its architecture or qualification framework wholesale: not selected;
  evaluate curated knowledge in PR2 and later bounded design work.
- Keep or merely renumber the promised inverse releases: not selected; research
  candidates require their own scientific and maintainer decisions.
- Add custom editable loaders or native overlays: unnecessary for normal
  Python development; retain the standard backend mechanism.
