# Maintainer reassessment — decision register

**Purpose:** single compact, maintainer-owned index of historical capabilities and new research candidates in the v0.8-based reassessment. **Not** an implementation plan or authorization to change code, CI, public API or release commitments. [ADR 0027](../../docs/development/decisions/0027-v0.9-reboot-from-v0.8.md) remains the governing reboot decision.

**Sources:** [historical capability inventory](../../docs/development/reboot/requirements-inventory.md) (R-IDs), [evidence index](../../docs/development/reboot/evidence-index.md) (independent oracles), and focused [reassessment notes](potential-work/README.md). Historical acceptance of Checkpoints A/B or individual Phase C work is **not** adoption into the reboot; integrated C was unaccepted and D unfinished. Published v0.8 [R-B01–R-B03](../../docs/development/reboot/requirements-inventory.md#baseline) are baseline behavior, not proposals.

**Review status** is the current maintainer decision, independent of historical outcome:

- `pending`: not yet decided for the reboot.
- `selected`: maintainer chose the functional **direction**, but its concrete contract, implementation, migration and issue scope may remain undecided.
- `selected for research`: maintainer approved the research **question/direction** only; no design or implementation chosen.
- `existing`: already accepted in the present reboot.
- `deferred`: set aside historical implementation while retaining the underlying capability as a possible later question.
- Future statuses when justified: `specified` (contract agreed), `declined`, `delivered`. Do not infer them from legacy commits.

Review sequencing preference: settle absent or mathematics-affecting public APIs first, then bounded safety/numerical work; the goal is not to reimplement Voro++. This is a prioritization principle, not an accepted future release plan.

**Review priorities (HIGH/MEDIUM/LOW) are provisional queue labels, not approvals.** `pending` rows can have a high review priority; `selected for research` authorizes evaluating an idea, not adding a public API or promising solver guarantees. Mathematical expressivity is welcome, but numerical and failure contracts require separate scrutiny.

**Updated native/Voro++ decision (ADR 0028):** the former blanket pre-C++ gate requiring upstream reporting of both R-O02b and R-O03 is replaced by **per-defect triage against a pinned upstream `dev` revision**. Independently confirmed issues may warrant a minimal, separately approved local backport if absent upstream `dev`; persistent noncritical upstream defects can be deferred, but serious silent scientific failures require correction, sound refusal or a reviewed mitigation. Upstream reporting is case-specific, not a prerequisite to unrelated binding changes. See [ADR 0028](../../docs/development/decisions/0028-upstream-voro-vendor-policy.md); no particular vendor patch is authorized here.

**Selected G0 direction:** the independent research and closure audit under [issue #149](https://github.com/DeloneCommons/pyvoro2/issues/149) support the layered architecture accepted by [ADR 0029](../../docs/development/decisions/0029-image-qualified-geometry-and-optional-global-complex.md). Specify only the necessary periodic/image contracts in F1 before separately scoping G1a image-qualified observed contacts; G1b is optional restricted global assembly. Independent F2 and I0/I1 work can proceed in parallel. A realization-aware inverse facade I2 needs reliable G1a contacts, **not** G1b. See [functional sequencing](../../docs/development/plans/functional-sequencing.md). This is not an approved v0.9 release feature list.

Keep modest clarifications and follow-up thoughts in the **last comment column**; create a separate `potential-work/` note only for substantial new alternatives, evidence or scientific investigation. Work is authorized only through a separate explicit maintainer decision and the applicable ADR/issue/PR process.
